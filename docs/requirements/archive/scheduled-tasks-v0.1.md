# 定时任务功能需求规格说明

项目：codex-weixin-Research  
文档编号：SRS-SCHED-001  
版本：0.1，需求评审草案  
日期：2026-11-02  
基线：当前微信桥接、项目记忆与 Codex 执行链路；尚未实现调度功能。

> 本文描述拟开发功能。标为“建议默认”的数值和产品取舍尚待需求评审，不代表已经获得用户确认。本文不新增实际定时任务，不规定数据库、调度库或 API 的最终实现。

## 1. 目标与成功标准

用户可以通过微信或本地 Web 管理页，保存“何时、对哪个项目、做什么”的任务；到点后由本机桥接执行，留下可追踪结果，并按策略通知原用户。

首版交付应使用户能够：

1. 建立一次性、每日、每周或固定间隔任务，并看到准确的下一次运行时间。
2. 查看、修改、暂停、恢复、删除任务，手动执行一次并查看历史结果。
3. 重启后保留任务；知道错过的触发是跳过、补跑还是等待处理。
4. 区分任务执行结果和微信发送结果，避免“日志成功但手机没收到”被误报为完成交付。
5. 让项目任务使用已选项目的记忆与技能，不读取无关项目，也不把工作目录猜成项目。

## 2. 参考 Codex 的部分与本产品取舍

依据 [OpenAI Scheduled tasks 官方文档][S1] 与 [Best practices][S2]：

| 参考能力 | 本产品拟采用的方式 |
| --- | --- |
| 保存任务提示、选择项目、时间和模型配置 | 保存可独立执行的任务定义，明确项目和执行范围 |
| 任务管理页与运行记录 | 本地 Web“定时任务”页，微信提供对应管理入口 |
| 独立运行或继续原会话 | 首版每轮独立新建 Codex 会话；继续原会话列入后续版本 |
| 技能定义工作方法，任务定义时间 | 保存技能引用，需要时读取技能正文 |
| 本地任务依赖电脑与应用运行 | 首版依赖本机桥接服务；不承诺关机或休眠期间执行 |
| Git 工作目录或隔离 worktree | 首版以读取、分析、报告为主；自动改代码和 worktree 执行后续设计 |

以上是能力参考，不声称复刻官方内部实现。下文的补跑、并发、重试和通知规则均为本项目的需求提案。

## 3. 使用者、术语与边界

- **任务 Task**：持久化的工作描述、触发计划、所有者、项目、权限和通知策略。
- **触发 Occurrence**：时间计划产生的一次应执行时刻。
- **运行 Run**：一次实际执行尝试，保存输入快照、会话、产物、状态与错误。
- **通知 Notification**：把某次运行结果发往微信的独立操作。
- **所有者 Owner**：任务所属的桥接账号与已授权联系人；Web 操作继承现有访问控制。
- **项目**：用户在 `global_memory.md` 中明确登记的项目，使用稳定 projectId。目录名称不构成项目身份。

首版为本机单服务实例，沿用现有多微信账号隔离。本地 Web 是管理与查看入口，微信是创建、管理和通知入口。调度由桥接自身持有，不依赖某个聊天窗口保持打开，也不是替用户配置 Codex 桌面应用的官方 Scheduled 功能。

## 4. 首版范围

### 4.1 必须包含（P0）

- 一次性、每日、每周、固定间隔四类时间计划，明确 IANA 时区。
- 微信自然语言创建、结构化任务操作入口，以及 Web 任务列表、编辑表单、运行详情。
- 创建、查看、编辑、暂停、恢复、删除、立即运行、停止本次运行。
- 项目任务与通用任务；每轮独立会话；提示、模型和权限配置可追溯。
- 持久化、重启恢复、漏跑记录、并发控制、崩溃后不确定状态处理。
- 结果本地保存；微信发送状态独立管理；发送失败不重新执行任务。
- 账号隔离、任务参数校验、工具权限约束及可测试的时间行为。

### 4.2 后续范围（P1/P2）

继续既有会话的跟进任务、条件满足后自动结束、任意 RRULE/cron 编辑、多项目单任务、自动改代码与 worktree、云端执行、系统开机服务、事件触发、日历/邮箱集成、分布式调度、严格费用预算。

首版不自动启动训练、部署、合并提交或发送消息给第三方。这些操作需要单独设计授权范围与执行约束，不能由“允许定时运行”推导出来。

## 5. 典型用户故事

| ID | 用户故事 | 期望结果 |
| --- | --- | --- |
| US-01 | 每天北京时间 09:00 汇总某研究项目的近期进度 | 读取指定项目的资料，生成摘要和依据，推送微信 |
| US-02 | 30 分钟后提醒我检查结果 | 一次性提醒，按期运行，完成后不再触发 |
| US-03 | 每隔 30 分钟检查指定运行是否结束 | 调用已允许的只读检查；未变化时安静，变化或失败时通知 |
| US-04 | 暂停周报，随后修改到周五 18:00 再恢复 | 暂停期间不执行，恢复后显示新的下一次时间 |

示例中的提醒文本、项目与检查对象均由用户指定，不内置任何个人项目或服务器地址。

## 6. 功能需求

### 6.1 创建与管理

| ID | 需求与可观察结果 |
| --- | --- |
| FR-01 | 微信接受自然语言创建意图。没有明确要求定时执行的普通聊天，不创建任务。解析结果必须由服务端结构化校验，不能仅凭模型说“已创建”认为保存成功。 |
| FR-02 | 信息明确时直接保存并回执，不要求机械的第二次确认。时间、项目、接收人或工作范围有实质歧义时先澄清；草稿不触发执行。 |
| FR-03 | 回执包含任务 ID、名称、任务内容、项目或“通用任务”、时区、可读计划、下一次时间、通知方式。面向微信不要求用户读 cron/RRULE。 |
| FR-04 | 微信和 Web 均可列出与查看任务、修改内容和时间、暂停及恢复、删除、立即运行。操作以稳定任务 ID 定位；重名时不能任意选中一个。 |
| FR-05 | 删除使任务退出未来调度，但保留已有运行记录；暂停不删除定义。暂停、删除和修改均持久化。运行中的行为见 FR-15。 |
| FR-06 | 修改生成新任务修订号。已开始运行继续使用启动时快照；尚未开始的旧修订排队项失效。停止本次运行是独立操作，不能把暂停误当成终止。 |
| FR-07 | 同一入站微信消息重放或相同创建请求重试，只创建一份任务；用户有意另建相同任务时允许创建，不单凭同名或同提示去重。 |

微信命令入口可采用 `/tasks`、`/tasks show <id>`、`pause/resume/run/stop/delete <id>`；最终语法在接口设计阶段确定。现有 `/new`、`/stop` 的含义不得被隐式改变。

### 6.2 时间语义

| ID | 需求与可观察结果 |
| --- | --- |
| FR-08 | 支持指定日期时刻、每日时刻、每周选定星期与时刻、固定间隔。建议首版间隔不小于 5 分钟，以避免意外高频消耗；上限和格式由服务端校验。 |
| FR-09 | 所有任务保存显式 IANA 时区，建议实例默认 Asia/Shanghai；内部时刻用 UTC，界面同时展示当地时间和时区。修改电脑时区不改变已保存任务。 |
| FR-10 | 每日/每周按当地墙上时钟计算，固定间隔以创建或显式修改后的锚点计算，不随上一轮完成时间漂移。立即运行不改变正常计划。 |
| FR-11 | 相对时间以服务端收到有效请求的时刻为准，并在回执转换成具体日期时刻。过去的一次性时间、非法时区或无法唯一确定的“周五晚上”等输入必须提示处理，不能悄悄改期。 |
| FR-12 | 夏令时不存在的当地时刻跳过该次；重复的当地时刻只触发第一次，并在历史中可查。系统时钟回拨不重复运行已经持久记录的触发；向前跳变按漏跑政策处理。 |

### 6.3 执行、上下文与资源

| ID | 需求与可观察结果 |
| --- | --- |
| FR-13 | 到期时根据任务快照创建独立运行和新的 Codex 会话，不自动接续创建任务时的聊天历史。完整上下文必须来自保存的提示、全局入口、绑定项目、技能引用和实际资料。 |
| FR-14 | 项目绑定是用户保存任务时的持续项目选择。到期后允许按该 projectId 读取其项目记忆与相关技能，无需再次发送“继续项目”。不加载其他项目；不因 scheduler 的 cwd 而改变目标。 |
| FR-15 | 建议首版同一任务最多一轮在执行、实例最多一轮定时运行。到期时同任务仍在运行，记录该次 skipped_overlap，不堆积。其他任务按到期顺序排队；启动前重新检查修订、状态和资源条件。暂停/删除取消未启动排队项，正在执行的一轮继续，除非用户另行停止。 |
| FR-16 | 定时工作不插入或中断正在进行的普通聊天 turn，也不向聊天线程抢占注入提示。对同一受保护工作目录的操作冲突时等待；默认不强行终止前台任务。等待过期必须留下记录。 |
| FR-17 | 保存模型/推理设置的选择方式：实例默认或显式指定。每轮记录实际解析出的模型、推理档位和权限。指定模型不可用时明确失败，不偷偷更换模型或权限。 |
| FR-18 | 建议每轮超时 15 分钟，可配置。超时/停止需要终止本轮可控制的执行，不只修改界面状态。若无法确认子进程已结束，标为需核查并阻止重叠，不宣称已停止。远程子任务不能据本地停止推断已经终止。 |
| FR-19 | 创建时验证项目是否登记、位置是否明确、工作区是否允许；执行时再次验证。失效或变更的绑定标记 blocked 并说明原因，不自动寻找替代目录。远程任务使用登记服务器、项目路径和已有 MCP/技能；不缓存登录秘密。 |
| FR-20 | 首版任务以只读检查、分析、报告和提醒为范围。模型输出与服务端运行记录可以保存到任务结果目录；项目记忆、项目文件及远程数据的修改不因定时任务而自动获得授权。任务执行必须受工具层与现有权限机制约束，不能仅依赖提示词声称“只读”。尚不能约束的工具操作应阻止执行并说明。 |

通用提醒可以不调用模型；需要 agent 分析的任务复用 Codex 执行链路。任务不能自行创建下一层定时任务，除非以后增加明确的管理授权功能。

### 6.4 持久化、漏跑与重试

| ID | 需求与可观察结果 |
| --- | --- |
| FR-21 | 服务确认创建/修改成功前必须持久化。重启后恢复定义、暂停状态、修订、下一次时间、运行与通知记录。重复扫描同一触发不能产生第二份正常执行。 |
| FR-22 | 首版建议固定漏跑政策：有效调度/排队开始超过应执行时刻 5 分钟的触发不自动补跑。一次性任务标记 missed，需用户手动处理；重复任务合并记录漏跑数量并计算下一次未来触发，不逐次补跑。正常资源排队也适用该启动期限。界面必须告知该政策。 |
| FR-23 | 到期实例必须先持久化唯一触发身份和运行状态再执行。崩溃后，已经 running 但未确认结束的运行标记 interrupted/unknown；不得自动重新调用模型或工具，以免重复副作用。尚未开始的 queued 项按修订、启动期限和状态恢复。 |
| FR-24 | 首版不自动重跑失败、超时或中断的完整任务。用户“重新运行”产生新的 runId 并关联原运行；正常的下一次周期仍按计划执行。连续失败可汇总提示，但不静默暂停任务。 |

这些要求提供触发去重与可恢复记录，**不承诺外部副作用的 exactly-once**。调用远程工具后立刻崩溃时，必须保留不确定性供核查。

### 6.5 结果与微信通知

| ID | 需求与可观察结果 |
| --- | --- |
| FR-25 | 每轮保存摘要、完整结果、产物引用、错误、耗时与输入快照。微信不可用时结果仍可由 Web 查看。先保存结果，再提交通知。 |
| FR-26 | 支持 always（默认）、findings_or_failure、muted 三种策略。muted 只关闭微信通知；所有运行仍留记录。findings_or_failure 的“发现”标准必须保存在提示中，模型无法明确判定时不能偷偷当作无发现。 |
| FR-27 | 通知只能发给保存时绑定的桥接账号与原已授权联系人，不能使用“最后活跃联系人”代替。任务 ID、runId、结果状态与时间清楚可辨；遵守微信正文与附件格式约定。 |
| FR-28 | 执行状态和通知状态独立。微信 API 接受只能标记 api_accepted，不能标记用户已收到。首版若无真实送达回执，不展示 delivered。 |
| FR-29 | 微信登录失效、上下文失效或发送失败时保留待处理通知，不重新执行任务。新鲜入站消息恢复合法发送条件后，可向原接收人发送一条合并摘要；也可在 Web 手动只重发通知。未知发送结果不能盲目自动重试，避免重复。明确拒绝且恢复条件满足时允许单独重发。 |
| FR-30 | 一次性任务的唯一触发产生终态记录后进入 completed，包括执行失败、漏跑或中断；completed 表示计划已消费，不代表执行成功或用户已收到。通知失败独立可见，允许手动重跑。删除任务不删除既有结果，但取消尚未发送的通知，避免删除后继续推送。 |

Web 结果页是首版的持久结果入口，微信是通知通道；不能以微信是否显示消息判断任务是否执行过。

### 6.6 访问与运行前检查

- FR-31：账号 A 不能查看、修改、触发或接收账号 B 的任务；原账号/联系人失效时不转移所有权。用户明确停用账号或移除联系人后，阻止其任务的新运行和通知。
- FR-32：任务提示与参数、历史结果视为私有实例数据，不写入 Git 仓库，不复制凭据。Web 管理请求沿用现有认证、Origin 和请求令牌校验。
- FR-33：无人值守运行不能临时等待无人回应的审批或暗中放宽权限。需要交互的工具调用标记 blocked 并提示用户处理；恢复权限不自动重放失败的完整运行。
- FR-34：只登记任务不等于远程训练、修改仓库或第三方通信授权。若后续支持可写任务，需另行定义权限快照、范围与隔离需求。

### 6.7 监控类任务的连续状态

- FR-35：对于“只在变化时通知”的任务，每轮新会话可以获得该任务最近一次有效观察摘要作为比较数据，不接续旧聊天、不读取其他任务历史。观察数据持久化在任务运行状态中，不写入全局或项目长期记忆。
- FR-36：任务必须明确比较对象、变化/完成条件和首次观察规则。建议首次有效观察仅建立基线；失败、需要用户处理或判定不明时必须通知，不能当作“无变化”静默处理。有效新观察与运行结果一起保存；通知失败不阻止保存观察，但仍保留待处理通知。
- FR-37：当选择 findings_or_failure 时，执行链路必须输出并校验“有发现/无发现/无法判定”及其依据；只凭自然语言为空或未出现关键词不能决定静默。历史观察仅作为数据，不作为新工具指令。

## 7. 概念数据与状态

下列为需求所需信息，不是最终表结构。

**Task**：taskId、ownerAccountId、ownerSenderId、名称、prompt、projectId/null、技能引用、计划类型/参数、timezone、锚点、下一次时间、修订号、状态、模型/推理选择、执行范围、超时、通知策略、创建/更新时间。

**Run**：runId、taskId/revision、scheduledAt、触发来源、快照、queued/started/endedAt、Codex threadId（如有）、执行状态、错误分类、摘要、结果/产物位置、模型与权限实际值。

**Notification**：notificationId、runId、原所有者、状态、发送尝试时间与计数、错误、恢复条件；不保存或输出登录 token。

任务状态：draft、active、paused、completed、deleted。blocked 描述某次运行及阻止原因，重复任务未来触发仍会重新校验。

执行状态：queued、running、succeeded、failed、timed_out、stopped、blocked、interrupted_unknown、missed、skipped_overlap、cancelled_before_start。

通知状态：not_required、pending、api_accepted、failed、unknown、cancelled。不存在真实回执时不设置 delivered。

## 8. 非功能需求

| ID | 要求 |
| --- | --- |
| NFR-01 | Windows + Node.js 24 是首版验收环境；保持现有跨平台入口。关闭网页不影响调度，退出桥接进程则停止；不自动安装系统常驻服务。 |
| NFR-02 | 在单实例、无排队/资源阻塞的验收环境中，到期扫描/入队延迟不超过 60 秒；这不是模型完成时间保证。时间语义必须可用虚拟时钟测试。 |
| NFR-03 | 保存操作崩溃后不得留下半份定义或误报保存成功；版本演进需能检测格式不兼容，不能丢弃原数据后“恢复默认”。 |
| NFR-04 | 任务 CRUD 不要求模型在线；自然语言解析、模型执行或微信服务故障不得阻止用户在 Web 暂停任务和查看已存结果。 |
| NFR-05 | 所有日志通过 taskId/runId/触发时刻关联；区分调度、模型、工具、存储与发送错误，避免在日志中泄露凭据。 |
| NFR-06 | 建议默认每账号最多 20 个 active 任务；允许配置。保存前展示频率与潜在模型消耗，不宣称可精确预测费用。首版不无限重试。 |
| NFR-07 | 运行历史不因删除任务而静默删除；首版支持查看保存位置与人工归档，自动清理与保留周期后续单独约定。 |

## 9. 必须通过的验收场景

| ID | Given / When | Then |
| --- | --- | --- |
| AC-01 | 已授权用户提出明确的每日 09:00 任务 | 持久保存一次，回执含时区和下次时刻；同一消息重放不重复创建 |
| AC-02 | 用户只说“以后经常关注一下”，或项目/时间不明确 | 不启动任务；返回需要澄清的信息或未激活草稿 |
| AC-03 | 服务重启，任务处于 paused | 保留 paused；不触发；恢复后显示未来下一次时间 |
| AC-04 | 一次性触发已启动，服务重扫或时钟回拨 | 不产生第二次正常执行；结束后不再被日常扫描触发 |
| AC-05 | 周期任务正在执行，又到下一时刻 | 记录 skipped_overlap；不启动第二轮、不积压同任务补跑 |
| AC-06 | 服务离线错过一天的多个触发，再启动 | 不批量补跑；周期任务合并记录漏跑，指向未来触发；一次性任务标记 missed |
| AC-07 | 任务排队时被暂停、删除或修订 | 旧排队项不执行；已经 running 的快照不被悄悄修改 |
| AC-08 | 保存独立项目任务，运行 cwd 是默认工作区 | 每轮新会话读全局入口及选中项目记忆，目标不变；不读其他项目或把 cwd 登记成项目 |
| AC-09 | 项目路径未指定、被移除，或所需工具权限不足 | 创建时不激活或运行时 blocked，明确原因，不猜路径、不提升权限 |
| AC-10 | 模型成功，微信返回 API 成功但无送达回执 | 本地结果 succeeded，通知 api_accepted；界面不写“用户已收到” |
| AC-11 | 模型成功，但微信发送失败/上下文过期 | 保存结果与待处理通知；只重发通知不会增加模型执行次数；原接收人不变 |
| AC-12 | 执行或通知提交后服务崩溃，结束状态未知 | 标记不确定，不自动重放模型/外部副作用；用户可查看并选择后续处理 |
| AC-13 | 用户请求停止、或本轮超时 | 尝试停止实际执行并记录；无法确认结束时显示需核查并禁止重叠 |
| AC-14 | A 的任务 ID 被 B 通过微信或 Web 提交 | 访问被拒绝，不泄露 A 的提示或结果 |
| AC-15 | 模型生成含附件的结果，或监控策略为 findings_or_failure | 结果可在 Web 查看；附件走原发送机制；新会话使用同任务观察基线，无变化静默，变化/失败/判定不明通知 |
| AC-16 | 修改本机时区，或在 DST 跳过/重复时刻调度 | 已保存时区保持不变；按 FR-12 的确定规则产生触发记录 |
| AC-17 | 手动立即运行一个 active 周期任务 | 有独立 runId，遵守并发约束，原 nextRunAt 不漂移 |
| AC-18 | 删除带待处理通知的任务，或移除所有者授权 | 停止后续执行与通知，旧结果保留供有权用户查看 |

## 10. 首版完成定义（Definition of Done）

- P0 需求与 AC-01～AC-18 可追踪到测试或演示记录；时间、恢复和去重用确定性测试，不用长时间 sleep 验证。
- 微信与 Web 至少走通创建、管理、一次执行、查结果、停止/失败及通知重发链路。
- 使用隔离数据验证调度，真实模型与微信验收需要明确测试对象；不得为测试启动真实训练、发送给无关联系人或更改生产项目。
- 类型检查、构建及新增测试通过；既有测试失败单独对照基线记录，不能把全量未通过写成“全部通过”。
- 文档说明本机运行条件、漏跑、并发、超时、数据位置、费用影响和送达状态；给出启动/关闭方式。
- 实现前形成单独的技术设计（ADR/设计文档），再拆分数据持久化、时间计算、执行编排、微信/Web 管理及通知交付任务。

## 11. 待评审的产品决策

本草案采用以下建议，以便评审后形成稳定需求基线：

1. 首版以只读任务为范围，代码修改和自动训练推迟；是否满足第一个真实用例？
2. 首版采用独立新会话，已有聊天的持续跟进放后续版本。
3. 固定间隔下限 5 分钟、启动宽限 5 分钟、执行超时 15 分钟、实例定时并发 1、每账号 active 上限 20。
4. 漏跑默认跳过，完整执行不自动重试；发送失败独立恢复。
5. 默认 always 通知，允许 findings_or_failure 与 muted；没有真正送达回执时只报告 API 接受状态。
6. 本地 Web 必须作为可查的结果入口，微信与 Web 都提供首版基本管理能力。

这些选择由需求评审确认后冻结。之后新增 worktree、可写权限、云端或持续会话时，增补需求而非在实现中偷偷扩大首版。
