# 定时任务与科研自动化需求说明

项目：codex-weixin-Research  
文档编号：SRS-SCHED-001  
版本：0.2，已评审需求基线  
日期：2026-11-02  
状态：用户于 2026-11-02 认可本版并要求进入 system design；替代 v0.1，尚未进入功能实现。

> 产品定位：以通用定时能力为基础，让研究者通过微信管理远程实验、GPU 资源、研究结果与文献跟踪。不能以“能够定时发消息”作为科研版本交付完成的标准。

## 1. 本次修订依据

v0.1 的通用调度部分已得到用户认可，但“首版只读”“训练启动后置”“条件完成后停止后置”等限制不能满足本项目定位。本版保留其时间、持久化、管理、隔离、记忆与通知要求，重新定义科研范围。

用户于 2026-11-02 明确要求覆盖六类科研用途：

1. 远程实验定时启动。
2. 训练监控与完成通知。
3. 结果整理与实验对比。
4. 文献追踪。
5. 显卡占用情况检测。
6. 自动占显卡，并明确两种方式都要：空闲后直接启动实验；先运行占卡进程保留 GPU、随后启动实验。

这些是本版首个科研版本的交付范围，可以分阶段实现，但不能全部推到未来版本，只交付通用定时器。

本文件规定“需要达到什么行为”。模块、接口、数据库、调度库、协议及具体命令属于后续 technical specification。本文不构成创建实际任务、运行实验或占用 GPU 的操作指令。

## 2. 产品目标与成功标准

用户能够把一个明确的科研意图保存为可持续执行的任务，例如：

- “今晚 23:00 在指定服务器启动这个实验，结束后检查指标并告诉我。”
- “每 15 分钟检查训练；正常推进时安静，结束、报错或停滞时通知。”
- “监测我指定的服务器，找到符合条件的 GPU 后启动已配置实验。”
- “空出卡时先保留一张，最多保留 30 分钟，我准备好后交给指定实验。”
- “每天整理新完成实验，与指定 baseline 对比，给出证据和结果文件。”
- “每周汇总指定研究方向的新论文，去重并附来源。”

首个科研版本的成功标准是：用户可以用微信或 Web 建立和管理这些任务，查看真实执行证据，并在桥接重启、服务器失联或微信发送失败时保留可靠状态，避免重复提交实验、错误宣称完成或失去 GPU 保留记录。

系统辅助研究工作，不自动把一次程序运行升级为“实验有效”“方法优于 baseline”或“研究目标已完成”。

## 3. 使用者、对象与部署边界

| 对象 | 含义 |
| --- | --- |
| Task（任务） | 用户保存的意图、时间/条件、项目、动作范围和通知策略 |
| Occurrence（触发） | 一次到期或获准进入下一阶段的机会 |
| Control Run（控制回合） | 一次检查、提交、收集或模型分析，可在短时间内结束 |
| Research Job（科研作业） | 实际实验、训练或评估进程，可能在远程运行数小时或数天 |
| Observation（观察） | 对作业、GPU、指标或文献来源的一次带时间和证据的观测 |
| Resource Lease（资源保留） | 有身份、范围、到期时刻和释放责任的临时 GPU 占用 |
| Workflow（科研流程） | 提交 → 监控 → 产物验收 → 报告等已声明阶段 |
| Notification（通知） | 将某个结果或状态变化发往原用户的独立操作 |
| Owner（所有者） | 桥接账号与已授权联系人组成的任务身份 |
| Project（项目） | 全局记忆入口中明确登记的项目，使用稳定 projectId |
| Recipe（执行方案） | 已定义的命令/脚本、参数、环境、输入输出、资源与允许动作 |

首版继续采用本机桥接服务。关闭网页不影响调度；电脑关机、休眠或桥接退出时，本地不能继续触发和观测。已经在远程可靠启动的作业可继续运行，但这不代表本地仍在监控或能及时发微信。

本版不承诺云端全天在线、多机分布式调度、完整集群调度器或无限自治研究。服务器已有资源调度机制时应接入它，不声称绕过它即可获得正式资源预留。

## 4. 交付范围与阶段

### 4.1 三个必须交付的能力层

| 层 | 内容 | 是否首个科研版本必须 |
| --- | --- | --- |
| G：通用基础 | 时间计划、CRUD、持久化、重启、权限、结果、微信/Web | 是 |
| R：科研作业 | 实验定时启动、可靠身份、长期监控、完成验收、结果对比、文献追踪 | 是 |
| GPU：资源管理 | 占用检测、条件启动、先占卡后交接、限时释放 | 是，两种占卡方式均包含 |

### 4.2 建议实现顺序

1. G：先完成通用时间与状态基础。
2. R/GPU 观察：接入现有服务器能力，完成训练/GPU 检测和变化通知。
3. R/GPU 执行：支持明确执行方案、条件启动、资源保留与交接。
4. R 产物：完成结果验收、实验对比和文献任务。
5. 联调：验证实验启动 → 监控 → 结果整理 → 微信通知，以及故障恢复。

可以分别发布中间里程碑，但必须明确“通用预览”“科研部分完成”“科研首版完成”，不能在只有第一步时宣称需求全部完成。

### 4.3 后续扩展

任意 DAG 可视化编辑、模型自行生成并无限尝试实验、自动大规模超参搜索、跨项目全自动决策、自动改代码与 worktree、云端托管、外部邮箱/Slack/GitHub 事件、多用户集群抢占、费用精确计费均不属于本轮必须实现内容。

这里的“后续扩展”不包括本轮已明确要求的实验启动和两种自动占卡模式。

## 5. 用户场景与预期结果

| ID | 场景 | 预期结果 |
| --- | --- | --- |
| US-01 | 通用提醒、每日/每周汇总 | 保存并按计划执行；信息明确时直接创建并回执 |
| US-02 | 今晚启动一个远程实验 | 校验明确方案与范围；可靠提交一次；返回作业身份 |
| US-03 | 每 15 分钟检查训练 | 报告阶段、指标与证据；无变化不打扰 |
| US-04 | 训练结束后整理结果 | 验证退出状态和产物；失败与产物不完整分开报告 |
| US-05 | 与 baseline 比较多个实验 | 标明数据集、划分、指标、方向、版本与可比性 |
| US-06 | 每周跟踪指定研究主题的新论文 | 按配置来源和时间窗口检索、去重、保留链接和筛选理由 |
| US-07 | 看指定服务器哪些卡能用 | 同时检查显存、进程、利用率、可见性和观测时间 |
| US-08 | 一有空卡就启动已配置实验 | 在截止时间内等待条件，启动前复查，避免重复或抢错卡 |
| US-09 | 有空卡时先帮我占住，稍后跑实验 | 创建限时占卡进程和 lease；可以交接、查看和释放 |
| US-10 | 实验在跑，本机重启了 | 重新核对原作业，恢复观测，不从头再启动一个 |
| US-11 | 微信没收到完成通知 | Web 仍可查证据；可只重发通知，不重跑实验 |
| US-12 | 暂停监控、停止实验、释放占卡 | 三种不同动作分别执行，不把“停监控”变成“杀训练” |

所有示例目标、路径、命令、预算和接收人都由用户或项目配置确定。示例不内置个人服务器地址、凭据或实验参数。

## 6. 通用功能需求

### 6.1 创建与管理

| ID | 需求 |
| --- | --- |
| FR-01 | 微信接受明确的自然语言定时/科研任务意图，Web 提供结构化表单。普通讨论不自动创建；服务端必须校验并持久化，不能仅由模型声称创建成功。 |
| FR-02 | 信息充分且动作已获授权时直接保存并回执，不机械重复确认。实质歧义或缺少项目、执行方案、资源范围时保存 draft 并说明；draft 不执行。 |
| FR-03 | 回执包含 ID、任务类型、内容、项目/目标、时区、时间/条件、下一次检查、动作范围、通知策略和相关期限。科研执行任务另展示目标服务器与执行方案。 |
| FR-04 | 微信和 Web 支持列表、详情、编辑、暂停、恢复、删除、立即执行和历史查看。使用稳定 ID 定位；重名不任意匹配。科研扩展还支持作业与 lease 详情。 |
| FR-05 | 暂停/删除持久化并阻止未来动作；保留历史。运行中作业和 GPU 的处理按第 9 节执行，不能隐式把远程训练杀掉。 |
| FR-06 | 编辑生成新修订。已开始控制回合和已提交作业保留原方案快照；旧修订未开始动作失效。 |
| FR-07 | 同一入站消息或管理请求重试不重复建任务。用户有意另建同名/同内容任务允许创建。 |

微信入口至少能区分任务管理、停止本轮、停止远程作业、释放占卡与重发通知。命令语法在 specification 中确定；现有 /new、/stop 不隐式更改含义。

### 6.2 时间、等待与触发

| ID | 需求 |
| --- | --- |
| FR-08 | 支持一次性、每日、每周、固定间隔。agent 周期任务默认最小 5 分钟；轻量 GPU 采样与资源条件检查单独配置，不要求每次调用模型，也不受该 5 分钟下限限制。 |
| FR-09 | 保存显式 IANA 时区，实例默认 Asia/Shanghai；内部时间使用 UTC。界面显示日期、时间与时区，本机时区变化不改变已保存计划。 |
| FR-10 | 每日/每周按当地时刻；间隔任务按锚点计算，不随上轮结束漂移。立即执行不改变原周期。 |
| FR-11 | 相对时间以有效请求接收时刻计算，回执给具体时刻；过去的一次性时间、非法时区、含糊时间不得静默改期。 |
| FR-12 | DST 不存在的时刻跳过，重复时刻只触发第一次；时钟回拨不重复执行已登记触发。向前跳变按适用的漏跑/恢复规则处理。 |

必须区分四类时限：计划触发的启动宽限、已进入资源等待的截止时间、控制回合超时、远程作业/资源保留期限。不能用“5 分钟漏跑”结束一个用户明确允许等到明早的 GPU 任务。

### 6.3 上下文、并发与执行范围

| ID | 需求 |
| --- | --- |
| FR-13 | 每个 agent 控制回合默认新建会话；输入来自保存任务、全局入口、选中项目、相关技能、关联作业和有限观察基线。不能依赖创建时聊天仍有上下文。 |
| FR-14 | 项目绑定视为用户保存的持续项目选择，允许读取该项目记忆与相关技能。不加载无关项目；不根据 cwd 推断项目；通用任务不预读全部项目。 |
| FR-15 | 同任务控制回合不重叠，实例默认 agent 定时并发 1。轻量采样和远程长作业使用独立限额；一项远程训练不能占满整个桥接的控制槽位。 |
| FR-16 | 不向前台聊天注入定时提示、不强制中断前台工作；冲突的项目修改/提交受协调。查看、暂停、停止、释放等管理操作不排在长实验之后。 |
| FR-17 | 保存模型/推理设置的默认或显式选择，每轮记录解析值。指定模型不可用时明确失败，不静默替换。 |
| FR-18 | 控制回合默认超时 15 分钟；不等同于远程实验最长运行时间。停止或超时要作用于真实控制执行；结束不确定时保留 unknown，并阻止重复提交。 |
| FR-19 | 创建与执行时校验登记项目、位置、目标和工作区范围。未知路径不使用默认 cwd 替代；远程路径不作为 Windows 本地路径处理。 |
| FR-20 | 默认只读；允许用户明确配置的实验提交、结果写入、有限 GPU 保留/释放。保存动作能力、项目/服务器/路径、方案版本及预算；工具层执行约束，不能只依赖“只读”提示词。 |

长期记忆不是授权文件。允许执行某次或某类固定实验，不代表允许模型自行更换训练目标、修改数据或扩大 GPU 数量。

### 6.4 持久化、恢复与重试

| ID | 需求 |
| --- | --- |
| FR-21 | 确认创建/修改成功前持久化；重启保留修订、状态、下一时刻、作业、观察、lease、运行与通知记录。同一触发不产生第二次正常执行。 |
| FR-22 | 普通时间触发默认启动宽限 5 分钟，超时不补跑；周期漏跑合并记录。科研任务若已合法进入 waiting_resources，则按其等待期限继续；监控重启后补一次当前状态核对，不重放所有漏掉的采样。 |
| FR-23 | 外部动作前登记唯一操作身份与意图。重启后先核对原作业/lease；不能确认是否成功的提交标记 unknown，不自动重提。只读观测可受限重试，但不能伪造缺失期间的历史。 |
| FR-24 | 不自动重跑整项失败实验。仅允许任务预先声明的重试方案与次数；每次关联原作业、保留原因。显存不足、连接错误、数据错误等不同失败不能一律从头重跑。 |

本系统要求可靠去重和状态核对，不承诺任意远程副作用 exactly-once。无法核实时必须暴露不确定性。

### 6.5 结果、通知与隔离

| ID | 需求 |
| --- | --- |
| FR-25 | 先保存结果和证据，再通知。模型结果、远程作业状态、产物验收结果分别记录；微信不可用时 Web 仍可查看。 |
| FR-26 | 支持 always、findings_or_failure、muted。通用任务默认 always；训练/GPU 监控默认 findings_or_failure，无变化保持安静。完成、失败、需要处理、明确资源状态变化按任务策略通知。 |
| FR-27 | 只通知绑定的原账号与授权联系人；禁止以最后活跃联系人代替。内容包含任务/作业身份、时间、变化、证据摘要与必要操作。 |
| FR-28 | 微信 API 接受仅标记 api_accepted；无真实送达回执时不能写 delivered 或“手机已收到”。 |
| FR-29 | 发送失败与执行失败独立。保留待处理通知，恢复合法发送条件后合并提示；支持只重发通知。未知发送结果不盲目重试，不因发送失败重新训练或占卡。 |
| FR-30 | 单次计划耗尽不等于科研流程完成。提交、训练、验收、报告与通知分别展示；已授权的后续监控不能在首次提交后提前退出。删除取消未来动作和待发通知，但保留历史。 |
| FR-31 | 账号/联系人之间隔离；所有者停用或移除后不把任务转给别人。阻止其新动作，已经运行的作业/lease 按声明的取消与到期规则处理。 |
| FR-32 | 实例任务、实验记录和结果为私有状态，不进入源码仓库；不复制凭据。Web 沿用现有认证、Origin 与请求令牌约束。 |
| FR-33 | 无人值守动作依赖已保存的合法能力；需要临时审批时 blocked 并通知，不能无限等待或绕过 never 策略。 |
| FR-34 | 创建某个科研任务可包含明确的预授权范围，授权不必每轮重问；超出方案、目标、资源或重试预算则不得自动扩权。 |

### 6.6 连续观察

| ID | 需求 |
| --- | --- |
| FR-35 | 持久化同任务最近有效观察、关联作业和必要阶段；新会话可以使用它们作为数据，不接续旧聊天，不读取其他任务历史。 |
| FR-36 | 监控保存比较对象、变化/完成条件、异常阈值和停止条件。首次正常采样默认建基线；作业已终止、异常或需处理则立即按规则报告；达到监控终点后停止轮询。GPU 保留成功属于明确事件，需要通知。 |
| FR-37 | “有发现/无发现/无法判定”必须结构化并附依据；判定不明不能当无变化静默。历史输出、论文和日志均作为数据，不能变成新增指令或授权。 |

## 7. 科研专项需求

### 7.1 项目上下文与执行方案

| ID | 需求与验收依据 |
| --- | --- |
| RFR-01 | 科研执行/实验对比绑定 projectId；GPU 资源巡检可只绑定明确服务器范围，文献追踪可绑定研究主题或项目。未开始的项目不猜路径或自动建立实验目标。 |
| RFR-02 | 科研任务保存目标服务器 canonical alias、远程目录、recipe、环境引用、参数、输入数据引用、输出位置、资源需求和完成标准；缺失执行所需字段时不能激活启动类任务。 |
| RFR-03 | 每次提交保存不可变实验快照：方案版本、命令/参数、代码版本或 dirty/unknown 状态、环境引用、数据版本/路径、seed（如适用）、预期指标与输出。无法取得的元数据明确记 unknown，不伪造可复现性。 |
| RFR-04 | 对已保存的服务器、方案、写入位置和资源范围执行预授权检查；创建明确的启动任务可构成其范围内的持续授权。模型不自行改命令、扩大数据范围、增加 GPU 或循环试验。 |

### 7.2 远程实验定时启动

| ID | 需求与验收依据 |
| --- | --- |
| RFR-05 | 使用项目登记的服务器连接技能和现有 MCP 能力，显式指定 canonical server alias。工具不可用、审批拒绝或主机身份不符时报告 blocked，不改用 shell SSH 或读取凭据文件绕过。 |
| RFR-06 | 长作业使用项目规定的持久执行方式；当前 PolyU 项目遵守已有 tmux 约定，若另有已配置作业调度器则使用对应方式。提交返回可重查的作业身份、日志/结果位置和启动证据；不能依赖一条长连接不断开。 |
| RFR-07 | 每次明确的实验尝试具有稳定操作身份，按作业标识、启动记录或调度器身份查重。MCP 超时后先核对是否已启动；未知时保持待核查，不启动第二份。用户明确要求的新一次复现或下一周期实验使用新 job 身份；不能仅按 taskId 或相同命令永久去重，阻止合法重复实验。 |
| RFR-08 | 定时启动支持“固定时刻尝试”和“从指定时间开始等资源”两种语义。后者包含资源条件、最大等待时间、允许重试的只读检查和启动后监控策略。 |

“实验启动成功”的证据必须包含系统能再次定位的真实进程/作业身份；仅收到命令文本、创建 tmux 会话或模型一句“已启动”不够。

### 7.3 GPU 检测、自动启动与先占卡

| ID | 需求与验收依据 |
| --- | --- |
| RFR-09 | 对明确服务器范围实时采样 GPU 身份、可见设备索引/UUID、总/已用/空闲显存、利用率、活动进程及观测时间；权限不可见字段标记 unavailable。不能依据 alias 或旧记忆推断当前 GPU。 |
| RFR-10 | 可用条件由任务定义：卡型号/候选设备、数量、每卡最低空闲显存、允许占用阈值、是否允许共享、连续满足次数。0% 利用率不等于空闲；他人进程仍占显存时不能误报可独占使用。 |
| RFR-11 | 模式 A：发现条件满足后直接启动已配置真实实验。启动前重新核对 GPU 与资源范围，记录选择原因和实际设备映射，避免设备索引变化导致启动到错误 GPU。 |
| RFR-12 | 模式 B：发现空闲资源后先启动独立占卡进程，以 Resource Lease 记录持有者、设备、占用量、开始/到期时刻、进程身份及待交接方案。占用行为必须可观察、可释放，不把普通采样或创建空会话算作保留成功。 |
| RFR-13 | 占卡前声明服务器、GPU 数量/候选范围、目标显存占用量、最长保留时间和到期动作。默认不以空转计算制造满负载；保留有明确期限，不默认无限续期。 |
| RFR-14 | 支持查看/提前释放/按明确方案交接 lease。交接记录释放与实验启动的实际结果；不假设两者原子完成。竞争丢卡或启动失败时按原等待期限恢复等待或报告失败，不错误宣称交接成功。 |
| RFR-15 | 保留进程必须有远端可执行的到期释放机制；本机退出、桥接崩溃或网络断开也不能导致无限占卡。无法保证到期释放时不得启动保留模式。释放只能作用于可靠识别的本任务占卡进程，不能清理他人进程。 |
| RFR-16 | 等待资源期间区分“条件未满足”“观测失败”“权限不可见”“资源保留中”。保存等待截止时间，超时停止新占用并通知。原始 GPU 采样跨任务复用，避免每个任务重复高频探测或每次调用模型。 |

显存占用进程只能证明实际占用的资源，不当然获得整张卡计算资源的排他权，也不等于集群调度器正式 reservation。没有可验证的独占分配机制时，界面要显示“已占用指定显存，排他性未保证”，不能显示“独占 GPU 已锁定”。

### 7.4 训练监控与完成通知

| ID | 需求与验收依据 |
| --- | --- |
| RFR-17 | 监控依据持久作业身份、日志游标/更新时间、阶段、指标、退出记录和产物；支持用户已有作业的显式登记，不要求由本系统启动。多个作业以各自身份隔离。 |
| RFR-18 | 明确区分 running、succeeded、failed、stalled/suspected、unreachable、unknown。服务器失联不等于训练失败，GPU 降至 0% 或 tmux 消失不等于训练成功。 |
| RFR-19 | 完成标准可包含退出码、完成标记、必须存在的 checkpoint/指标/报告和校验条件。状态冲突或证据不足则 needs_review，不直接报告成功。 |
| RFR-20 | 支持日志停滞、异常退出、OOM、无效指标、缺失产物、超出运行预算等任务明确指定的异常检测。阈值按阶段配置；合法的长评估不能因短期无日志被误判为确定失败。 |
| RFR-21 | 无变化安静；有意义进展、完成、失败、停滞或需要用户处理时通知，并对同一状态持续重复去重。失联恢复后可报告恢复与实际变化；终态验证后停止轮询，除非用户另设后续任务。 |

### 7.5 结果整理、实验对比与证据

| ID | 需求与验收依据 |
| --- | --- |
| RFR-22 | 结束后按配置收集日志摘要、指标、checkpoint/图表/报告引用和验收结论；保留服务器路径、观察时间与校验结果。产物存在与产物正确性分别记录；默认不下载整个数据集或大模型。 |

| RFR-24 | 输出可查看的结构化结果表与人类可读摘要，包含真实值、差值、缺失项、证据位置和局限。需要图表/报告文件时写入任务允许输出区，并引用对应运行身份。 |

## 8. 资源、授权和预算

### 8.1 动作能力

| 能力 | 例子 | 约束 |
| --- | --- | --- |
| observe | 读日志、GPU 检测、查询作业 | 默认可选，遵守已授权目标和读取范围 |
| artifact_write | 保存指标表、报告、文献索引 | 限定输出区，不修改源数据或代码 |
| job_submit | 执行保存的实验方案 | 绑定方案、服务器、项目、次数和资源 |
| gpu_reserve | 启动占卡进程 | 绑定设备范围、显存量、保留期限与远端释放机制 |
| gpu_release | 释放本任务保留 | 可靠进程/lease 身份核对，不以 GPU 索引杀全部进程 |
| job_stop | 停止实际实验 | 需包含该动作授权，核对作业身份，记录执行证据 |
| project_memory_update | 写入核实里程碑 | 仅选中项目、仅允许内容，不改全局授权 |

这是行为范围，不预先决定必须使用哪种协议或字段实现。用户已在任务中明确授予的能力不重复询问；缺少关键范围或超出范围时才需要处理。

### 8.2 必须有界的资源

启动/占卡任务必须声明 GPU 数量、内存/显存需求、允许目标、最大等待和保留期限。实验最长时长、最大提交次数、重试次数、下载量和通知量按任务类型配置；若没有授权自动停止实验，达到时长阈值应通知，不能擅自杀进程。

多任务竞争相同资源时必须显示等待与优先顺序，不允许两个任务把同一张卡都登记成自己已独占。采样到空闲只是观测，启动/占用操作还要实时复查；本系统内部排队不承诺阻止外部使用者同时抢到资源。

禁止把“空闲卡出现”自动解释为允许清理别人的显存、结束别人的训练或改变服务器资源管理配置。

## 9. 生命周期与故障语义

### 9.1 必须分别表达的状态

| 维度 | 最少需要区分 |
| --- | --- |
| 时间计划 | draft、active、paused、已耗尽、deleted |
| 控制回合 | queued、running、succeeded、failed、blocked、timed_out、interrupted_unknown、missed、skipped |
| 科研流程 | 等待时间、等待资源、保留中、提交中、监控中、验收中、完成、失败、待处理 |
| 远程作业 | 提交待核查、排队、运行、结束待验收、成功、失败、未知 |
| 资源保留 | 申请中、持有中、交接中、已释放、已到期、释放待核查 |
| 通知 | not_required、pending、api_accepted、failed、unknown、cancelled |

最终枚举名可在 specification 确定，但不能合并以上不同事实。比如“提交回合 succeeded；作业 running；通知 api_accepted”是合法组合。

### 9.2 停止和删除

- **暂停时间计划**：停止新触发；不自动杀作业。对已有科研流程，界面必须显式选择暂停哪些自动阶段。
- **停止监控**：停止后续观测和推送；作业保持运行，已有 lease 仍按远端期限释放。
- **停止控制回合**：中止本轮检查/分析；已提交作业不能因此被认为已停止。
- **停止实验**：通过作业身份执行已授权终止，并验证结果；未知状态不能宣称成功。
- **释放占卡**：只结束本任务的保留进程；已交接给真实实验的 GPU 不再按纯 lease 清理。
- **删除任务**：取消未开始的动作和待发通知，保留历史；纯占卡资源尝试释放，失联则依靠远端到期机制并显示待核查。运行中的真实实验不隐式终止。
- **禁用账号/移除所有者**：禁止新提交、续期和通知；不失去远端到期释放机制，不把资源转给其他联系人。

### 9.3 故障处理要求

| 故障 | 需要发生的行为 |
| --- | --- |
| 本机离线错过启动 | 按计划宽限记 missed；不在重启时盲目补提交 |
| 本机离线期间远程实验继续 | 恢复后核对原 job，补一次当前状态观察，不重启实验 |
| 提交请求超时 | 根据操作身份核对；证据不足为 unknown，不直接再提交 |
| GPU 观测失败 | 标明无法观测，不把旧值标成实时空闲 |
| 占卡时目标被别人使用 | 失败/回到合法等待，不结束对方进程 |
| 保留时本地崩溃 | 远端期限仍生效；恢复后核对 lease，不创建第二份 |
| 交接失败 | 分别记录 lease 是否释放、实验是否启动，按剩余期限处理 |
| 实验退出码为 0 但缺指标 | 结束待验收/needs_review，不宣称科研任务成功 |
| 微信发送失败 | 保留结果与待发事件，不重启实验、不再次占卡 |
| 模型/工具不可用 | 结构化管理仍可用；blocked/failed 可追踪，不改为未声明执行方式 |

## 10. 概念数据与科研产物

本节定义需要保存的信息，不是数据库表结构。

- **Task**：所有者、任务类型、项目/研究主题、时间/条件、目标、方案与能力、预算、通知策略、修订、计划状态、期限。
- **Control Run**：触发来源、任务修订、时间、会话、输入快照、实际模型/权限、执行结果、错误及关联 job/lease。
- **Research Job**：提交操作身份、项目、服务器/目录、外部作业/进程身份、方案快照、资源、日志/产物位置、观测游标、运行与验收状态。
- **Resource Lease**：设备稳定身份、持有进程、显存量、所有者、目标方案、开始/到期、远端释放机制、交接与核对结果。
- **Observation**：目标、采样时间、来源、数据、有效性、前次有效观察引用、变化与判定证据。
- **Workflow**：阶段及版本、关联对象、已完成条件、下一步、截止时间和需要人工处理的信息。
- **Research Result**：指标及定义、实验对比、输入来源、产物引用、校验、解释与局限。
- **Literature Item**：稳定标识、来源及日期、版本、项目/主题、阅读层级、筛选理由、已发现/已通知状态。
- **Notification**：事件身份、目标原联系人、对应结果/作业、尝试记录与 API 接受状态。

不把密码、私钥、登录 token 存入这些对象。重现所需的环境引用与可公开参数应保存；敏感值使用现有凭据引用，不复制到报告。

| agent 定时最小间隔 | 5 分钟 | 不限制专用轻量采样 |

| 单控制回合超时 | 15 分钟 | 不作为远程实验超时 |
| agent 定时并发 | 1 | 远程作业不长期占据此槽位 |
| 每账号 active 任务上限 | 20，可配置 | 资源扫描可被多个任务共享 |
| 轻量 GPU 检测周期 | 建议 15 秒，最小 5 秒 | 新增建议；按服务器/连接能力限速 |
| 普通训练监控周期 | 建议 15 分钟，可配置 | 新增建议；不必每轮模型分析 |
| GPU 保留期限 | 建议默认 30 分钟 | 新增建议；每次必须有明确上限 |
| 资源等待期限 | 用户/项目明确指定 | 不默认无限等待 |
| 自动完整实验重试 | 默认 0 | 可显式配置固定方案和次数 |
| 研究监控通知 | 有变化/完成/失败/需处理 | 不定时重复发送无变化摘要 |
| 普通任务通知 | always | 可改策略 |
| 通知送达语义 | API 接受与实际送达分开 | 无回执不声称 delivered |

前六项沿用 v0.1 基础取值并调整适用边界。用户已认可本版，科研新增数值作为首版默认基线，仍保留表中声明的可配置性；两种自动占卡模式均为必须交付能力。

## 12. 验收场景

### 12.1 通用验收（延续并修订原 AC 编号）

| ID | 操作/条件 | 必须观察到的结果 |
| --- | --- | --- |
| AC-01 | 明确创建每日任务并重放同一消息 | 只创建一次，回执含时区、范围与下一次时间 |
| AC-02 | 时间、项目或执行方案有关键缺失 | 草稿/澄清，不擅自激活 |
| AC-03 | 暂停后重启、再恢复 | 状态保留，暂停不触发，恢复计算未来计划 |
| AC-04 | 同一触发重扫或时钟回拨 | 不重复控制动作或提交 |
| AC-05 | 同任务控制回合尚未结束再次到期 | 不重叠；远程训练仍可被后续独立控制回合观测 |
| AC-06 | 离线后恢复 | 普通漏跑不批量补；远程作业核对和合法资源等待分别恢复 |
| AC-07 | 编辑/删除排队任务 | 旧修订不执行，已提交作业仍保留原证据 |
| AC-08 | 默认 cwd 与目标项目不同 | 只用所选项目和技能，不加载全部项目记忆 |
| AC-09 | 未登记项目、无路径、MCP/权限不可用 | blocked/草稿，有原因，不猜路径或绕过权限 |
| AC-10 | 微信 API 成功但无送达回执 | 显示 api_accepted，不显示 delivered |
| AC-11 | 实验结果保存后发送失败 | Web 可查；只重发通知不增加实验/占卡次数 |
| AC-12 | 外部动作后崩溃、结果未知 | 恢复先核对；不能确认则 unknown，不自动重放 |
| AC-13 | 停止/超时 | 区分本轮、监控、作业和 lease 的实际结果 |
| AC-14 | 其他账号/联系人请求私有对象 | 无权访问，不泄露提示和结果 |
| AC-15 | 监控多轮无变化后出现异常 | 前者静默，异常有证据且通知去重 |
| AC-16 | DST 或本机时区变化 | 按保存时区和确定规则触发 |
| AC-17 | 手动执行周期任务 | 新控制记录，原计划不漂移；核对旧作业不重复提交，明确授权的新实验尝试使用新身份并遵守预算 |
| AC-18 | 删除/禁用所有者 | 无新动作/转发，历史保留，资源到期机制仍有效 |

### 12.2 科研验收

| ID | 场景 | 必须观察到的结果 |
| --- | --- | --- |
| RAC-01 | 按时启动已授权远程方案 | 唯一作业身份、方案快照、日志位置；控制回合结束后远程仍运行 |
| RAC-02 | 提交已被远程接受但回复丢失 | 核对原操作身份，不启动第二个实验 |
| RAC-03 | 实验运行超过 15 分钟 | 不因控制回合时限被杀；仍可独立检查 |
| RAC-04 | 已有作业运行期间重启桥接 | 恢复同一 job 监控，不重提、不丢观察 |
| RAC-05 | 服务器失联、GPU 0%、tmux 消失等 | 不能单凭这些报告训练成功/失败 |
| RAC-06 | 退出码 0，但必要指标/产物缺失 | needs_review 或验收失败，通知明确缺失证据 |
| RAC-07 | 多卡中某卡 0% 利用率但有他人显存进程 | 不误判为可独占卡；返回真实占用与时间 |
| RAC-08 | 模式 A 等到满足条件的 GPU | 启动前复查并仅启动一次，记录实际 GPU 映射 |
| RAC-09 | 模式 B 等到空卡并执行保留 | 真实占用可观测，产生 lease 和到期机制，通知用户 |
| RAC-10 | 占卡期间本机退出/断网 | 远端按期限释放；恢复可核对，不出现无限孤儿保留 |
| RAC-11 | 用户要求提前释放占卡 | 只释放自身 lease，不结束其他进程或已交接训练 |
| RAC-12 | 保留卡交接实验期间竞争丢卡/提交失败 | 分别记录释放与启动结果；不宣称成功，不杀竞争进程 |
| RAC-13 | GPU 等待超过 5 分钟，但未到用户指定期限 | 合法继续等；达到等待期限才结束并通知 |
| RAC-14 | 对比不同数据划分或定义不一致的指标 | 标注不可比，不输出不成立的提升结论 |
| RAC-15 | 完成实验结果整理 | 结构化表、证据路径、缺失/局限；不需要全量下载模型 |
| RAC-16 | 文献多来源返回重复项、旧项与新版本 | 去重并保留版本变化；日期和阅读层级明确 |
| RAC-17 | 部分文献来源失败/仅摘要可读 | 标注覆盖范围与阅读层级，不虚构全文结论 |
| RAC-18 | 从实验提交推进到报告 | 所有声明阶段可重启恢复；非声明新实验不会被擅自创建 |
| RAC-19 | 实验失败或显存不足 | 按保存重试策略处理；默认不无限从头训练 |
| RAC-20 | 多任务/多用户竞争同一 GPU，或索引变化 | 不把一张卡登记给多个内部独占任务，不按旧索引误杀/误用 |
| RAC-21 | 读取研究日志后产生里程碑 | 原始日志保留在运行记录；只在获准时更新所选项目记忆，不污染全局 |
| RAC-22 | 停监控/停实验/释放卡三种命令 | 动作、授权、目标与结果分别验证 |
| RAC-23 | 多个任务监测同服务器 | 共享有时间戳采样并限速；不每个采样启动一次模型 |
| RAC-24 | 先保留显存但无排他分配机制 | 展示实际占用与排他性未保证，不宣传已锁定整卡 |

## 13. 完成定义与评审要求

- FR-01～FR-37、RFR-01～RFR-34 和非功能需求有明确的实现/测试追踪。
- AC-01～AC-18、RAC-01～RAC-24 均有测试或受控演示证据，不把“模型说完成”视为端到端通过。
- 六类科研用途都能从微信/Web 建立、管理、追踪和查看结果，两种自动占卡模式都通过生命周期验收。
- 基础测试使用模拟远程能力、虚拟 GPU 和可控时钟；真实验收使用明确指定的测试目标与小规模任务，不拿真实长训练充当不可控测试。
- 类型检查、构建及新增测试通过；既有失败按基线说明，不虚报全量通过。
- 文档明确本地在线条件、远程作业持续性、资源保留限制、授权与停止语义、结果证据、通知状态及数据保存位置。
- 需求评审后再写技术 specification，重点解决执行去重、MCP 适配、GPU 保留/交接、远端期限、实验与控制回合分离、结构化证据和恢复。
- 新增科研默认数值可在评审调整，但不能用参数调整消除用户明确要求的能力。
